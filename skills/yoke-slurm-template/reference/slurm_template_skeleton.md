# SLURM Template Skeleton

The shared structure of Yoke's `training_slurm.tmpl` files (for example
`applications/harnesses/ch_ldrViT_lsc_cyl/training_slurm.tmpl` and
`applications/harnesses/vt_DDP_ldrViT/training_slurm.tmpl`), with the parts
that vary by machine marked.

There are two kinds of placeholder below. Keep them apart:

- `<KEY>`: harness tokens. Leave these **exactly** as written. Yoke fills
  them at study creation or on continuation.
- `@@NAME@@`: values **you** fill in from the interview when writing the
  file. None may remain in the written template.

## How Yoke renders the submission template

- `yoke-start-study` substitutes every CSV column `<KEY>` into it with plain
  text replacement (`yoke.helpers.strings.replace_keys`). The training
  submission template does **not** support `# <<optional:KEY>>` blocks. Only
  input templates and evaluation templates do.
- `<epochIDX>` and `<INPUTFILE>` are late-bound: `START` files get `0001` and
  `study###_START.input`. Continuation
  (`yoke.harnesses.base.HarnessStudy.continuation_setup`) fills them from the
  study's copy of this template on every restart.
- `<studyIDX>` renders as three zero-padded digits.
- A `<KEY>` with no CSV column is left as is, silently. Every `<KEY>` here
  must be a CSV column or one of the late-bound tokens.

Required tokens: `<studyIDX>`, `<epochIDX>`, `<KNODES>`, `<NGPUS>`,
`<train_script>`, `<INPUTFILE>`. Optional: `<allocation>` (recommended: it
keeps account names out of the template, so a changed allocation means
editing only the CSV).

## Training template

```bash
#!/bin/bash

# Yoke DDP training job for @@CLUSTER@@ (@@PARTITION@@ partition).
# Generated by the yoke-slurm-template skill on @@DATE@@; machine profile:
# skills/yoke-slurm-template/machines/@@CLUSTER@@.md
# @@NODE_NOTES@@  (e.g. "4x H100 per node, 288 CPUs, 2 threads per core")

#SBATCH --job-name=@@JOB_PREFIX@@_s<studyIDX>_e<epochIDX>
#SBATCH --account=<allocation>
#PRODUCTION
#SBATCH --partition=@@PARTITION@@
#SBATCH --time=@@WALLTIME@@
@@OPTIONAL_QOS_LINE@@
#DEBUG  (to use: comment out the PRODUCTION lines above, uncomment below)
#DEBUG  #SBATCH --partition=@@DEBUG_PARTITION@@
#DEBUG  #SBATCH --time=@@DEBUG_WALLTIME@@
#DEBUG  #SBATCH --qos=@@DEBUG_QOS@@
#DEBUG  #SBATCH --reservation=@@DEBUG_RESERVATION@@
#SBATCH --nodes=<KNODES>
#SBATCH --ntasks-per-node=<NGPUS>
#SBATCH --gpus-per-node=<NGPUS>
#SBATCH --cpus-per-task=@@CPUS_PER_TASK@@
@@OPTIONAL_MEM_AND_BINDING_LINES@@
#SBATCH --output=study<studyIDX>_epoch<epochIDX>.out
#SBATCH --error=study<studyIDX>_epoch<epochIDX>.err

# Rendezvous for torch.distributed: first node of the allocation, random port.
MASTER_ADDR=$(scontrol show hostnames $SLURM_JOB_NODELIST | head -n 1)
MASTER_PORT=$(shuf -i 1024-65535 -n 1)
export MASTER_ADDR MASTER_PORT

# Record the GPUs this job sees (useful when debugging allocations).
nvidia-smi

# NCCL inter-node interface on @@CLUSTER@@ compute nodes.
export NCCL_SOCKET_IFNAME=@@NCCL_IFNAME@@
# export NCCL_DEBUG=INFO
# export NCCL_DEBUG_SUBSYS=INIT

# Python environment with Yoke installed.
@@ENV_ACTIVATION_LINES@@

# Threads per rank (physical cores per task).
export OMP_NUM_THREADS=@@OMP_THREADS@@

export date00=`date`

# One rank per GPU; the train script reads its arguments from the @-file.
srun python -u <train_script> @<INPUTFILE>

export date01=`date`
echo "===================TIME STARTED==================="
echo $date00
echo "===================TIME FINISHED==================="
echo $date01
```

Fill-in rules:

- `@@OPTIONAL_QOS_LINE@@`: `#SBATCH --qos=<name>` if the site needs a QOS,
  otherwise delete the line.
- `@@OPTIONAL_MEM_AND_BINDING_LINES@@`: for example `#SBATCH
  --mem-per-gpu=120G`, `#SBATCH --gpu-bind=closest`, `#SBATCH
  --mem-bind=local`, or `#SBATCH --gres-flags=enforce-binding`, only as the
  profile or the user says. Otherwise delete the line.
- Delete the whole `#DEBUG` block if the user doesn't want it. Delete
  individual `#DEBUG` lines that don't apply (for example no reservation).
- If the user prefers a fixed account, replace `<allocation>` with it and
  note in the slurm card that the CSV needs no `allocation` column.
- The wall time must not exceed the partition's `MaxTime` or the QOS
  `maxwall`. It should fit the harness's `--cycle_epochs` (one job runs one
  cycle, then resubmits itself).

## Evaluation template (only if the harness opts into evaluation)

Evaluation is a separate single-GPU, non-DDP job. Its tokens are CSV keys
plus the late-bound `<CHECKPOINT>`, `<INPUTFILE>`, `<STEM>`, and
`<studyIDX>`. **Do not use `<epochIDX>`** here (see
`yoke.harnesses.base.HarnessStudy.evaluation_setup`). Based on
`applications/harnesses/ch_DDP_loderunner/evaluation_slurm.tmpl`:

```bash
#!/bin/bash
#SBATCH --job-name=@@JOB_PREFIX@@_eval_s<studyIDX>_<STEM>
#SBATCH --account=<allocation>
#SBATCH --partition=@@PARTITION@@
#SBATCH --time=@@EVAL_WALLTIME@@
#SBATCH --nodes=1
#SBATCH --ntasks-per-node=1
#SBATCH --gpus-per-node=1
#SBATCH --cpus-per-task=@@CPUS_PER_TASK@@
#SBATCH --output=eval_study<studyIDX>_<STEM>.out
#SBATCH --error=eval_study<studyIDX>_<STEM>.err

@@ENV_ACTIVATION_LINES@@
python -u @@EVAL_SCRIPT@@ @<INPUTFILE>
```

## Shell submission (no SLURM)

For `--submissionType shell`, the harness needs `training_shell.tmpl`
instead. It is run with `source`, and its last line runs
`python <train_script> @<INPUTFILE>` (see
`applications/harnesses/moving_mnist/training_shell.tmpl`). That is the
harness skill's job, not this one.

## Syntax check

After writing, check bash syntax on a copy with the `<...>` tokens replaced
by dummy values (`sed -E 's/<[A-Za-z_]+>/X/g' file > /tmp/x.sh; bash -n
/tmp/x.sh`), and grep that no `@@` remains.
